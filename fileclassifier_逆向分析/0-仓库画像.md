# 0. 仓库画像（类型判断 + 依据）

## 1. 仓库类型判断

| 维度 | 判断 | 依据 |
|------|------|------|
| **语言/栈** | Python 后端 + TS/React 前端（全栈，但后端权重最高） | `fileclassifier-python-api`（FastAPI）+ `fileclassifier-react-ui`（React18+Vite）两个子项目并存 |
| **领域/问题** | 数据处理·Pipeline（文件归档/匹配） | 核心是"按元数据把文件从输入目录挑出并复制到输出目录"，非 RAG / 非 Agent |
| **规模形态** | 全栈应用（monorepo，含桌面打包脚本） | 仓库根含 `build-windows/`、`dist-windows/`、`.ps1` 启动脚本与 governance 文档 |
| **成熟度** | 生产级（有测试、有部署文档、有桌面打包，但前端仍是 0.1.0） | `tests/` 覆盖核心服务层；`DEPLOYMENT.md` 完整；但 UI 版本号 `0.1.0`、`README` 自称 "minimal"，且有多个入口配置冗余 |

## 2. 仓库全貌（第 0.1 步）

### 顶层结构
```
fileclassifier/
├── fileclassifier-python-api/   # 后端核心（所有业务逻辑都在这里）
│   ├── src/fileclassifier/
│   │   ├── models.py            # dataclass 数据模型
│   │   ├── services/            # 业务逻辑层（神所在之处）
│   │   │   ├── file_matcher.py  # 列画像 + 文件匹配
│   │   │   ├── query_engine.py  # 条件过滤引擎
│   │   │   ├── workflow.py      # 编排：匹配→复制→报告
│   │   │   ├── excel_service.py # Excel 读写
│   │   │   └── mock_data.py     # 测试夹具生成器
│   │   ├── webapi/              # 接口层
│   │   │   ├── app.py           # FastAPI create_app / main
│   │   │   ├── main.py          # uvicorn 入口（端口 8000 写死）
│   │   │   ├── schemas.py       # Pydantic 响应模型
│   │   │   └── utils/           # pathing / serialization / system_io
│   │   └── tests/               # 5 个测试文件
│   ├── start_web.py             # Web 模式启动（端口 8000）
│   ├── start_desktop.py         # 桌面模式启动（端口 18080）
│   └── pyproject.toml           # 入口点 = webapi.main:main
├── fileclassifier-react-ui/     # 前端（三步向导式 UI）
│   └── src/App.jsx, components/, hooks/, lib/
├── legacy/                      # 早期 SVG/ps1 原型（已弃用）
├── build-windows/ dist-windows/ # Windows 桌面打包产物
├── start_web.ps1 stop_web.ps1 start_desktop.ps1
└── README.md / README.zh-CN.md / DEPLOYMENT.md / CHANGELOG.md
```

### 依赖清单（关键，决定"轻量"定位）
`fileclassifier-python-api/pyproject.toml`：
- **运行时依赖**：`pandas`、`openpyxl`、`fastapi`、`uvicorn`、`python-multipart`
- **测试**：`pytest`
- **本地**：`mypy`、`ruff`
- **web 可选**：`pyinstaller`（桌面打包用）
- **没有** 数据库、没有向量库、没有 ML 推理框架、没有 LLM SDK

> 这说明项目刻意保持"纯单机、零外部服务"的工程取向——这是后续所有设计取舍的总前提。

### 前端依赖（`fileclassifier-react-ui/package.json`）
- 运行时仅 `react` + `react-dom`（^18.3.1）
- 构建 `vite` + `@vitejs/plugin-react`
- **没有** 状态管理库（Redux/Zustand）、**没有** UI 组件库、表格是手写（无 ag-grid/tanstack-table）
- API 基址：`import.meta.env.VITE_API_BASE || "/api"`（`src/lib/api.js:1`）——说明生产靠反代把 `/api` 转到后端

### 入口点暴露（重要，存在冗余/矛盾）
| 入口 | 文件 | 端口 | 备注 |
|------|------|------|------|
| `pyproject.toml` console_scripts | `fileclassifier.webapi.main:main` | 8000（写死） | 但 `main()` 实际接受 `--port` 参数，README 却没用这个入口 |
| Web 启动脚本 | `start_web.py` | 8000 | 固定 `APP_PORT=8000` |
| 桌面启动脚本 | `start_desktop.py` | 18080 | 含 JSON 配置 + 环境变量覆盖 + 浏览器自启 + 健康探活 |

> ⚠️ **入口配置不一致（核实见核实清单）**：三个入口端口/配置互不统一；`pyproject.toml` 的 `main` 与 README 推荐的 `start_web.py` 是两套。属"坑"类，详情见 `4-设计取舍与坑.md`。
