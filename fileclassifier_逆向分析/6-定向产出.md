# 6. 定向产出（通用学习导向）

> 目的：如果你要做类似的东西，**第一步抄哪、第二步改哪**。

## 6.1 这个仓库"解决了什么形态的问题"
**问题形态**：用户手里有一张"元数据表（Excel）"和一堆"按某种规律命名、散落在磁盘的文件"，需要把"表里的每一条记录"对应到"磁盘上的某个文件"，并把命中的文件挑出来归档。本质是 **"结构化元数据 ↔ 非结构化文件名"的弱对齐 + 批量搬运**。

**外壳/交互**：三步向导式 Web UI（选表 → 设条件 → 执行），配桌面 exe 一键启动。无账号体系、无多租户、单机可信用户。

## 6.2 第一步：抄（最小可用骨架）
1. 抄 `services/file_matcher.py` 的 `analyze_columns` + `match_files` 骨架：列画像推断标识列 + 目录遍历子串匹配。这是整个项目的价值内核，约 250 行即可跑通。
2. 抄 `query_engine.py` 的 `MatchCondition` + `QueryEngine.filter`：用 dataclass 描述条件，pandas/纯 Python 求值，无需任何框架。
3. 抄 `webapi/app.py` 的薄路由 + `schemas.py`：把上面的 service 包成 3–4 个 REST 接口。
4. 抄 `start_web.py`：一个 `uvicorn.run` 脚本就能起服务。

→ 这一套能让你在 **半天内** 拥有"上传 Excel → 看匹配 → 复制文件"的可用工具。

## 6.3 第二步：改（按你的场景增强）
| 你的场景 | 改哪 | 怎么改 |
|----------|------|--------|
| 文件量巨大（10万+） | `match_files` 遍历 | 改 `os.scandir` + 并发；range 索引缓存 |
| 匹配要更准 | fuzzy 算子 | 换 `rapidfuzz`（可选依赖），并把 threshold 做成前端可调 |
| 多用户/云端 | 无状态 + 重算匹配已具备 | 加鉴权（FastAPI `Depends`）、把 `records` 存对象存储而非请求体往返 |
| 不止复制，还要移动/重命名/写库 | `workflow.py` | 抽象一个 `Action` 接口，复制只是其中一种实现 |
| 企业级前端 | React 手写表格 | 引入组件库 + 状态管理（当前 0.1.0 不值得直接扩） |
| 要审计追溯 | `write_report` + `append_log` 已有 | 加结构化日志/操作留痕表，支持回滚 |

## 6.4 不要抄的（反面教材）
- 多入口端口硬编码（`start_web`/`start_desktop`/`pyproject main` 三套不一致）→ 统一成一个 CLI。
- 前端 `/api` 双前缀隐患 → 明确反代契约，写进 README 或提供 `vite.config.js` proxy。
- 可能的 `storage` 死引用 → 提交前跑 `python -c "import fileclassifier.webapi.app"` 验证启动。

## 6.5 一句话方法论（可脱离本仓库沉淀）
**"弱结构对齐问题"的通用解法 = 自动推断键 + 子串/模糊匹配 + 可解释预览 + 服务端重算执行。** 把"算法不敢拍板的边界情形"显式交还给人类核对，比堆模型更稳妥、更省成本。
