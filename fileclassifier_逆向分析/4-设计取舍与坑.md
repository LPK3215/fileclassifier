# 4. 设计取舍与亮点 / 局限与坑

## 4.1 设计亮点（作者聪明的地方）

1. **零外部依赖的极致克制**
   运行时仅 pandas + openpyxl + fastapi + uvicorn。无 DB、无向量库、无 LLM。换来"下载即跑、单机可部署、无供应链风险"。对一个"帮人整理文件"的工具而言，这是正确的复杂度取舍。

2. **"预览—确认—执行"两段式 + 重算匹配（安全）**
   预览阶段产出 `MatchResult.context_before/after` 让人核对；执行阶段**服务端重算**匹配而非信任前端。避免了"客户端决定服务器复制什么"的越权风险（详见 `3-关键模块拆解` 模块 C）。

3. **可解释性优先于准确率**
   文件名子串 token 匹配 + context 回显，宁可多匹配也让人看见。对"误复制客户文件"这种高代价错误，把最终裁判权交给人，是务实的工程伦理。

4. **运行时目录抽象（`pathing.py`）**
   用单一函数收口桌面/Web 双模差异，业务层零感知。这是项目里最"成熟"的抽象。

5. **范围算子走二分索引（`query_engine._eval_range`）**
   在零依赖前提下，对数值范围过滤做了 O(log n) 优化而非逐行扫，体现对"Excel 几千行"真实体量的针对性。

6. **测试夹具即文档（`mock_data.py`）**
   边界情形（冲突/未索引/拼错）直接写进夹具路径名，测试意图自解释。

7. **dataclass 业务实体 + Pydantic 仅作 HTTP 边界**
   边界清晰，业务层可脱离 FastAPI 单测（`tests/` 正是这么干的）。

## 4.2 设计取舍（为某目标主动牺牲了什么）

| 取舍 | 得到 | 牺牲 |
|------|------|------|
| 零外部依赖 | 部署极简 | fuzzy 只能用 `difflib`，匹配质量弱于 fuzzywuzzy/rapidfuzz；无并发框架，大目录靠单线程遍历 |
| 子串 token 匹配 | 鲁棒、少漏配 | 可能过匹配（"AB" 命中 "ABC"），靠人工 context 复核兜底 |
| 全内存无状态 | 水平扩展友好 | 每次请求重传整个 `records`，大表（数万行）请求体膨胀、重算匹配重复 IO |
| 重算匹配 | 安全、防篡改 | 执行比预览多扫一遍目录，大目录下有可观延迟 |
| 单线程文件遍历 | 实现简单、无竞态 | 数十万文件级目录性能不足 |

## 4.3 局限与坑（含待核实隐患）

### 坑 1：多入口端口/配置不一致（已确认）
- `pyproject.toml` 的 `main` 入口端口写死 8000（`webapi/main.py`），`start_web.py` 也 8000，`start_desktop.py` 用 18080。
- README 推荐 `start_web.py`，但 `pyproject.toml` 的 console_scripts 指向 `webapi.main:main`——两套入口行为不完全一致（后者读 `HOST`/`PORT` 环境变量，前者固定）。
- **影响**：新手按 README 跑 `start_web.py` 与按 `pip install -e .` 后跑 `fileclassifier` 命令，配置来源不同，易踩端口/目录差异的坑。

### 坑 2：`storage.py` 被引用但缺失（⚠️ 待核实）
- `webapi/app.py` 启动事件里引用 `from fileclassifier.webapi.utils import storage` 相关逻辑（见 `1-架构全景` 图示），但 `src/fileclassifier/webapi/utils/` 目录实际只有 `pathing / serialization / system_io` 三个文件，`search_file` 未找到 `storage.py`。
- **可能解释**：历史重构遗留的死引用，或打包时被排除。需确认 `app.py` 是否真 import 了不存在的模块（若 import 在模块顶层，则启动会直接 `ModuleNotFoundError`）。
- **核实动作**：见 `核实清单.md`。

### 坑 3：前端 `/api` 前缀需外部反代（已确认）
- `src/lib/api.js:1` 用 `VITE_API_BASE || "/api"`，但 `webapi/app.py` 的路由前缀是 `/api/excel` 等（即完整路径含 `/api`）。
- **影响**：若前端 `base` 也是 `/api`，实际请求会变成 `/api/api/excel`。需 Vite dev proxy 或生产反代正确映射；仓库未提供 `vite.config.js` 的 proxy 段（⚠️ 待核实 vite 配置是否含 proxy）。

### 坑 4：前端版本 0.1.0 + 手写表格（已确认）
- 无组件库、无状态管理、表格手写。功能可用但可维护性/扩展性有限，且 `README` 自陈 "minimal"。适合个人/小团队工具，不宜直接当企业级前端基底。

### 坑 5：路径穿越防护未显见（⚠️ 待核实）
- `workflow._copy_file` 拼目标路径时，是否对 `output_dir` 做 `is_relative_to` 校验、是否防 `../` 穿越，需在源码层再确认（当前读取未覆盖该细节）。

### 坑 6：模糊匹配阈值硬编码（已确认）
- `query_engine` 的 fuzzy threshold 在代码内定值（非请求参数），用户无法在前端调灵敏度。`schemas.py` 暴露的条件里也没有 threshold 字段。

### 坑 7：大表性能天花板（推断）
- 全内存 + 单线程目录遍历，对"十万级文件 + 数万行 Excel"会明显变慢；当前定位是轻量工具，非海量场景。

## 4.4 作为分析者补充的改进建议
1. 统一入口：把 `start_web.py` / `start_desktop.py` / `pyproject` 的 `main` 收敛为一个 CLI（`argparse` 分支 web/desktop），消除配置漂移。
2. 修正或删除 `storage` 死引用，跑一次 `python -c "import fileclassifier.webapi.app"` 验证启动。
3. 把 fuzzy threshold 提升为可配置项（前端加滑块），并支持 rapidfuzz 作为可选加速。
4. 大目录遍历改用 `os.scandir` 或并发（`concurrent.futures`），并对 range 过滤器预热索引缓存。
5. 提供 `vite.config.js` 的 `/api` proxy 示例，或在 README 明示反代要求。
