## 1.2 依赖关系

- **依赖方向单向向下**：UI → webapi → services → models。无循环依赖。
- **services 层零框架耦合**：`file_matcher` / `query_engine` / `workflow` 只依赖标准库 + pandas，可在无 FastAPI 环境下直接 `import` 测试（这一点被 `tests/` 充分利用）。
- **webapi 是"薄层"**：`app.py` 只做路由注册 + 可选 CORS；各 router 仅做「参数接收 → 调 service → 包成 schema 返回」，无业务逻辑。
- **运行时目录抽象**：`utils/pathing.py` 用 `FILECLASSIFIER_DESKTOP_MODE` + `runtime_dir` 环境变量决定"用户数据/输出/日志"落在哪，使同一套代码既跑桌面（pyinstaller 单 exe）又跑 Web。这是连接双模部署的关键枢纽。

## 1.3 核心抽象

### （1）列画像 `ColumnProfile`（`file_matcher.py`）
对 Excel 每列计算：候选标识列概率（`is_identifier_candidate`）、基数（`cardinality`）、唯一值占比（`uniqueness_ratio`）、缺失率、是否含数值范围。这是"自动推断标识列"的基石。

### （2）匹配条件 `MatchCondition`（`query_engine.py`）
`{column, type, value/value2, case_insensitive, blank_handling}` 构成条件 DSL。支持 4 种算子（exact/contains/fuzzy/range）。工作流里多数条件作用于"标识列"，由 `build_matcher` 把命中记录映射成"应在磁盘上找的文件标识集合"。

### （3）匹配结果 `MatchResult`（`models.py`）
承载 `matched_files / unmatched_files / matched_records / unmatched_records / duplicates / conflicts / summary`，是贯穿"预览→执行"的唯一数据契约。前端的两个 summary 响应（`MatchDetailResponse` / `MatchSummaryResponse`）都是它的投影。

### （4）运行时目录上下文 `get_runtime_dirs()`（`pathing.py`）
把"部署形态差异"收敛成一个函数返回值，避免业务代码到处 `if desktop`。

## 1.4 设计风格的元判断
- **"薄接口 + 厚业务 + dataclass 实体"**：典型脚本型工程师把单机工具工程化的写法，而非企业级分层（无 repository/unit-of-work/DI）。
- **善用 dataclass 而非 Pydantic 贯穿业务层**：业务层用 `dataclass`，仅在 HTTP 边界用 Pydantic，边界清晰、测试友好。
- **显式、可解释、可审计** 优先于"智能/自动"：所有匹配都产出 `MatchResult` 让人核对，再决定是否执行复制——这是整库的设计哲学。
